# 1. Executive Summary

Platform adalah marketplace dan sistem pengelolaan sewa hunian yang mempertemukan:

- **PENYEWA** yang mencari kamar kos, rumah kontrakan, atau rumah sewa.
- **PENYEDIA KONTRAKAN** yang menawarkan dan mengelola unit hunian.
- **ADMIN DAERAH/KOTA** yang melakukan moderasi dan pengelolaan pada wilayah tertentu.
- **SUPER ADMIN** yang mengelola platform secara global.

Platform dirancang sejak awal untuk multi-region sehingga dapat dimulai dari satu daerah dan berkembang ke banyak kota/provinsi hingga skala nasional.

Model properti menggunakan:

**Provider → Property → Unit → Listing**

MVP menggunakan **Individual Listing**, yaitu satu unit yang dapat disewa direpresentasikan sebagai satu listing individual.

Platform tidak hanya berfungsi sebagai katalog. MVP juga mencakup alur transaksi:

**Search → Detail → Application → Provider Decision → Reservation → Payment → Contract → Rental → Billing → Renewal/Completion**

# 2. Product Goals

## 2.1 Goal Utama

Membangun platform yang membuat proses mencari, memilih, mengajukan, membayar, dan mengelola sewa hunian menjadi lebih terstruktur, transparan, dan mudah dilakukan secara online.

## 2.2 Goal untuk PENYEWA

- Menemukan hunian sesuai kebutuhan.
- Mendapat informasi listing yang lebih lengkap.
- Mengetahui lokasi dan status ketersediaan.
- Membandingkan pilihan.
- Mengajukan sewa tanpa harus selalu datang langsung.
- Mendapat proses approval yang jelas.
- Membayar melalui platform.
- Memiliki kontrak dan riwayat transaksi.
- Mendapat pengingat pembayaran.
- Memiliki mekanisme dispute/refund.

## 2.3 Goal untuk PENYEDIA

- Mempromosikan unit secara terstruktur.
- Mengelola banyak property/unit/listing.
- Mengetahui unit yang tersedia.
- Mengelola pengajuan penyewa.
- Mengelola penyewa aktif.
- Mengelola kontrak dan pembayaran.
- Mendapat laporan dasar.
- Memiliki mekanisme monetisasi platform yang jelas.

## 2.4 Goal Platform

- Mendukung multi-region.
- Menyediakan moderasi.
- Menyediakan audit trail.
- Mendukung transaksi yang dapat ditelusuri.
- Memiliki fondasi untuk scale-up nasional.
- Memisahkan domain marketplace, rental, billing, moderation, dan platform administration.

# 16. Provider Decision

## Approve

Ketika provider approve:

1. Application menjadi approved.
2. Unit dapat berubah menjadi RESERVED.
3. Reservation dibuat.
4. Tenant diarahkan ke payment.
5. Reservation memiliki expiration window.

## Reject

Ketika provider reject:

1. Application menjadi rejected.
2. Alasan wajib disimpan.
3. Tenant menerima notifikasi.
4. Tidak ada payment yang boleh diproses untuk application tersebut.

# 48. Acceptance Criteria — MVP

## AC-001 Marketplace

Given listing telah approved dan aktif, when user mencari berdasarkan lokasi/filter, then listing yang sesuai dapat ditampilkan.

## AC-002 Application

Given tenant login dan required data lengkap, when tenant mengajukan rental, then application tercatat dan provider menerima notification.

## AC-003 Provider Approval

Given provider menerima application, when provider approve, then reservation dibuat dan tenant dapat melanjutkan payment.

## AC-004 Provider Rejection

Given provider reject, then rejection reason wajib tersedia dan tenant menerima informasi tersebut.

## AC-005 Payment

Given reservation aktif, when payment sukses, then transaction tercatat dan contract dapat dibuat.

## AC-006 Contract

Given payment sukses dan validation selesai, then contract aktif menyimpan snapshot rental terms.

## AC-007 Recurring Billing

Given contract 6 bulan dengan monthly schedule, then sistem membuat billing schedule untuk periode yang sesuai.

## AC-008 Late Payment

Given invoice melewati due date tetapi masih dalam grace period, then rental tetap active dan tenant menerima warning.

## AC-009 Overdue

Given grace period berakhir, then invoice menjadi overdue dan warning diberikan.

## AC-010 Listing Fee

Given provider memiliki active listing capacity, then occupied listing tidak mengurangi capacity aktif.

## AC-011 Listing Expiry

Given listing fee expired, then listing tidak menerima application baru tetapi historical transaction tidak dihapus.

## AC-012 Audit

Given admin melakukan rejection/refund/suspension, then audit record tersimpan dengan actor, object, old state, new state, timestamp, dan reason.

## AC-013 Multi-region

Given provider memiliki property di dua kota, then masing-masing property dapat berada pada region dan moderation scope yang berbeda.

# 50. Risks

## RISK-001 — Payment Gateway Dependency

Settlement, refund, split payment, dan Gateway Fee handling sangat tergantung kemampuan gateway.

**Mitigation:** payment gateway belum dikunci sampai technical evaluation.

## RISK-002 — Listing Capacity Economics

Gap package 20 → 50 dapat menghasilkan biaya yang terasa melonjak.

**Mitigation:** evaluasi setelah data penggunaan awal.

## RISK-003 — Provider Reliability

Provider cancellation dapat merusak trust.

**Mitigation:** audit + warning + refund + reliability mechanism.

## RISK-004 — Marketplace Quality

Listing palsu/tidak akurat dapat menurunkan trust.

**Mitigation:** provider verification + listing moderation + reporting.

## RISK-005 — Operational Dispute Load

Dispute dapat meningkat ketika volume transaksi meningkat.

**Mitigation:** standard dispute workflow + evidence + escalation.

## RISK-006 — Multi-region Complexity

Moderation dan permission dapat menjadi kompleks.

**Mitigation:** scope-based authorization sejak awal.
